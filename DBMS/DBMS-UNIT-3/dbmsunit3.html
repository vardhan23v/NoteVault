Chapter 08

Overview of Storage and Indexing

Before any query runs, the DBMS must first find the data. This chapter explains how data is physically stored and how indexes make retrieval fast. Think of it as "how does the database know where things are?"

1.1 — Why Physical Storage Matters

A database must store enormous amounts of data — far too much to keep in RAM. This data lives on external storage (hard disks, SSDs). The DBMS must constantly move data between disk and main memory.

Think of a giant library. Your RAM is your desk — you can only work with a few books at a time. The disk is the shelves — unlimited space, but you have to physically walk to fetch a book. The DBMS "buffer manager" is the librarian who fetches books for you and keeps the most useful ones on your desk.

Two types of external storage are described:

  • Disks: Can retrieve any page at a fixed cost (random access). But reading several consecutive pages together is much cheaper than reading them scattered across the disk.
  • Tapes: Can only read pages sequentially (like rewinding a cassette). Much cheaper, used for archival backup only.
A Record ID (rid) is a unique physical address of a record — it tells the DBMS exactly which disk page and which slot on that page the record lives on. The rid is sufficient to physically locate any record.

1.2 — Three Alternative File Organizations

How do we physically arrange records on disk? There are three main strategies, each ideal for different workloads:

OrganizationHow records are arrangedBest forWeakness
Heap FileRandom order — new records added at end of fileFull file scans (fetch all records)Slow for searching specific records
Sorted FileRecords sorted by the value of some field(s)Range queries; ordered retrievalInserts/deletes are very expensive (must maintain order)
IndexA separate data structure that maps key values → record locationsFast lookup by specific key valueAdds storage overhead; updates also update the index

1.3 — What is an Index?

An index is a separate data structure that allows the DBMS to quickly find records matching certain field values — without scanning the entire file.

An index is exactly like the index at the back of a textbook. Instead of reading every page to find "B+ tree", you look it up alphabetically in the index and it tells you "page 247". The DBMS does the same thing: instead of scanning all records for employees in department 5, it uses an index on the Department field.
  • The field(s) used to look up records in an index is called the search key.
  • The search key is not the same as a primary key — it can be any subset of fields.
  • Multiple indexes can be built on the same file with different search keys.

1.4 — Three Alternatives for Data Entries in an Index

When you look up a key in an index, what does each index entry actually contain? There are three choices:

AlternativeWhat the index storesProsCons
Alt 1 The actual full data record itself (key + all fields) One lookup gets everything — no second fetch needed Only ONE index per file can use this. If two indexes used Alt 1, data would be duplicated and could become inconsistent. Large data records = large index.
Alt 2 <key value, rid of ONE matching record> Entries much smaller than full records. Many indexes can coexist on one file. Requires a second disk access to fetch the actual record after finding the rid.
Alt 3 <key value, LIST of rids of all matching records> Most compact when many records share the same key value. Variable-length entries (list can be long), which complicates storage management.
The choice of Alternative 1/2/3 is independent of whether you use a B+ tree or a hash as the index structure. You can have a B+ tree using Alt 2, or a hash using Alt 3, etc.

1.5 — Index Classification: Four Key Distinctions

1. Primary vs Secondary Index

  • Primary index: The search key contains the primary key of the relation. There can only be one.
  • Secondary index: Any other index. A table can have many secondary indexes.
  • Unique index: The search key contains a candidate key (all values are distinct).

2. Clustered vs Unclustered Index

This is the most important distinction and has a massive impact on performance.

A clustered index means the physical order of records on disk matches (or is close to) the logical order defined by the index search key. Only ONE clustered index is possible per file.

An unclustered index means the physical order of records on disk has nothing to do with the order of the index.

Visualization from the textbook — imagine data records scattered in a heap file, and index entries sorted by search key:

  • Clustered: The arrows from index entries to data records all point to records that are nearby on disk (low seek cost).
  • Unclustered: The arrows jump all over the disk — each record may require a separate I/O.
For a range query returning 1,000 matching records:
• Clustered index: ~10 disk pages (records are together) → very fast
• Unclustered index: up to 1,000 disk pages (one per record, scattered) → potentially 100× slower!

3. Dense vs Sparse Index

  • Dense index: One index entry per data record. Can answer queries without accessing the data file.
  • Sparse index: One index entry per page of data records. Smaller index, but can only be used with clustered data (since you need to scan within a page after finding it).

4. B+ Tree vs Hash-Based Indexes

  • Hash index: Uses a hash function to map key values to buckets. Very fast for equality searches (find exactly one value). Useless for range queries.
  • B+ Tree index: A balanced tree structure. Good for both equality and range searches. The most widely used index type.
Rule of thumb: Exact match query (age = 25)? Use hash. Range query (age BETWEEN 20 AND 30) or sorting? Use B+ tree.

1.6 — Cost Model for Comparing File Organizations

To compare different organizations, we use a simple cost model based on disk I/O (we ignore CPU costs since disk I/O dominates):

  • B = number of data pages in the file
  • R = number of records per page
  • D = average time to read or write one disk page
  • F = fanout of B+ tree (number of entries per index page, typically 133)

The 5 Operations and Their Costs

Why does sorted file have such expensive inserts? To maintain sorted order, you might need to shift all records after the insertion point — potentially moving O(B) pages. That's why sorted files are rarely used in practice; B+ trees give almost the same search benefits with much cheaper inserts.

Why does unclustered B+ tree range search cost BD(R + 0.15)? For each matching record, you need a separate random I/O. If 10% of records match (0.15B index pages), you might do up to R × 0.15B = 0.15BR random reads, where each could require fetching a separate page.

1.7 — How to Choose Indexes (Index Selection Guidelines)

Creating the right indexes is a critical design decision. Here are the key guidelines:

1
Attributes in WHERE clauses are candidates for index keys. If queries frequently filter on age or salary, those fields should be indexed.
2
Exact match → hash index. Range query → tree index. WHERE age = 25 works perfectly with hash. WHERE age BETWEEN 20 AND 30 needs a B+ tree.
3
Clustering is especially valuable for range queries. Since only one index can be clustered per table, choose the one that benefits the most important/frequent range queries.
4
Consider composite (multi-attribute) indexes for multi-condition WHERE clauses. WHERE age = 30 AND salary > 50000 benefits from a composite index on <age, sal>.
5
Order matters in composite indexes. Index on <age, sal> helps queries that filter on age (or age + sal). But it does NOT help queries that filter only on sal.
6
Consider index-only strategies. If all columns needed by a query are in the index, the DBMS never touches the actual data file.

1.8 — Composite Search Keys in Depth

Consider employees with fields: name, age, sal. We want to support queries on combinations of age and salary.

Data entries in an index on <sal, age> (sorted by sal first, then age):

Records: sue(age=13,sal=75), bob(age=12,sal=10), cal(age=11,sal=80), joe(age=20,sal=12)

<sal, age> index entries: (10,12), (12,20), (75,13), (80,11) — sorted by sal first
<age, sal> index entries: (11,80), (12,10), (13,75), (20,12) — sorted by age first

Query: age=20 AND sal=75
→ A composite <age,sal> index finds this instantly. Individual age or sal indexes would need more work.

Query: age=20 AND sal > 10
→ Clustered <age,sal> tree is best: go to age=20 entries, then scan forward while sal > 10.

Query: age=30 AND 3000 < sal < 5000
→ <age,sal> is much better than <sal,age>. With <age,sal> you find age=30 entries and scan the sal range. With <sal,age> the sal range is spread across different "age" groups — not consecutive.

1.9 — Index-Only Plans

Sometimes a query can be answered entirely from the index, without touching the actual data pages at all. This is extremely fast.

QueryIndex needed for index-only plan
SELECT E.dno FROM Emp E GROUP BY E.dno<E.dno> (any index on dno)
SELECT E.dno, MIN(E.sal) FROM Emp E GROUP BY E.dnoTree index on <E.dno, E.sal>
SELECT AVG(E.sal) FROM Emp WHERE E.age=25 AND E.sal BETWEEN 3000 AND 5000Tree index on <E.age, E.sal> OR <E.sal, E.age>
SELECT D.mgr FROM Dept D, Emp E WHERE D.dno=E.dnoIndex on <E.dno> (only dno needed from Emp side)

For index-only plans, clustering doesn't matter — you never fetch data pages, so their physical order is irrelevant.

Trade-off to remember: Every index speeds up queries but slows down inserts/deletes/updates (because the index must also be updated). Also, indexes use disk space. Don't create indexes you don't need.
Chapter 09

Storing Data: Disks and Files

Before we can index or query data, we need to understand how data is physically stored on disk and how the DBMS manages moving it into memory. This chapter is the foundation of all database performance.

2.1 — Why Not Just Use RAM?

Two reasons we can't keep everything in main memory:

  • Cost: RAM is expensive. At the time the textbook was written: $1000 buys 128 MB of RAM OR 7.5 GB of disk. Even today, RAM costs orders of magnitude more per GB than disk.
  • Volatility: RAM is wiped when power is lost. Databases must persist data across shutdowns, crashes, and failures.
Storage Hierarchy:
1. Main memory (RAM) — for currently active data. Fast, expensive, volatile.
2. Disk (secondary storage) — for the main database. Slow, cheap, persistent.
3. Tapes (tertiary storage) — for archiving old data. Cheapest, sequential access only.

2.2 — How a Hard Disk Works

Understanding disk mechanics is essential because they determine why I/O is slow.

A hard disk consists of:
• Platters — circular disks that spin on a central spindle (e.g., 90 rotations per second)
• Tracks — concentric circles on each platter surface where data is written
• Sectors — fixed-size subdivisions of a track (the smallest physical unit)
• Disk heads — read/write heads that hover over the spinning platters
• Arm assembly — moves the heads in/out to position them on different tracks
• Cylinder — all tracks at the same arm position across all platters (an imaginary column)

How Long Does a Disk Access Take?

Reading or writing one block of data requires three sequential steps, each taking time:

1
Seek time: Move the arm to position the head over the correct track. Varies from 1ms to 20ms depending on how far the arm must move. This is usually the dominant cost.
2
Rotational delay: Wait for the disk to rotate until the desired block is under the head. Ranges from 0 to 10ms (on average ~5ms at 6000 rpm).
3
Transfer time: Actually move the bits from the magnetic surface to the controller. About 1ms per 4KB page. Relatively fast.

Total typical access time: 5–20ms per page. Compare this to RAM access at ~100 nanoseconds — disk I/O is roughly 100,000× slower than RAM access.

Seek time and rotational delay dominate the cost. Minimizing I/Os and keeping related data on the same track/cylinder is critical. This is why the order of pages on disk matters enormously for database performance.

Sequential vs Random I/O

The key insight: reading pages sequentially (next page on same track, then same cylinder, then adjacent cylinder) is much faster than random I/O because you avoid repeated seek and rotation costs.

  • Sequential scan: Pre-fetch multiple pages at once — very efficient.
  • Random access: Every access pays full seek + rotation cost — expensive.

This is why clustered indexes are so much faster for range queries than unclustered ones — a clustered index results in sequential reads.

2.3 — RAID: Making Disks Reliable and Fast

A single disk can fail. RAID (Redundant Array of Independent Disks) distributes data across multiple disks to improve performance and reliability.

Two core techniques:

  • Data striping: Split data into chunks (stripe units) and spread them across multiple disks. Multiple disks can be read in parallel — faster throughput.
  • Redundancy: Store extra information so data can be reconstructed if one disk fails.
RAID LevelMechanismReliabilityPerformanceNotes
Level 0Striping only, no redundancyNoneBest (parallel reads)Any disk failure = total data loss
Level 1Mirroring — exact copy on second diskHighParallel reads; writes hit 2 disks50% storage overhead
Level 0+1Striping + Mirroring combinedHighFull aggregate bandwidth for readsMost expensive
Level 3Bit-interleaved parity; 1 check diskModerate1 request at a time (all disks involved)Simple, older
Level 4Block-interleaved parity; 1 check diskModerateSmall reads parallel; writes bottleneck on check diskCheck disk is bottleneck
Level 5Block-interleaved distributed parityHighParity spread across all disks — no bottleneckMost popular for databases

2.4 — Disk Space Management

The lowest layer of the DBMS software is the disk space manager. It provides a simple abstraction to higher layers:

  • Allocate a new page
  • Deallocate (free) a page
  • Read a page from disk into memory
  • Write a page from memory to disk
When a higher layer requests a sequence of pages, the disk space manager must allocate them sequentially on disk. This ensures efficient sequential I/O for scans.

2.5 — The Buffer Manager

The DBMS cannot work on data that's on disk — it must bring it into RAM first. The buffer manager is the component responsible for this.

The buffer pool is a region of main memory divided into fixed-size frames. Each frame can hold one disk page. The buffer manager maintains a table of <frame#, pageID> pairs so it knows which disk page is currently in which frame.

What Happens When a Page is Requested?

1
Check buffer pool: Is the requested page already in a frame? If yes, just return its address — no disk I/O needed!
2
Choose a victim frame: If the page is not in the pool, pick a frame to replace using the replacement policy.
3
Write dirty page if necessary: If the chosen frame contains a page that was modified (dirty bit = 1), write it back to disk before evicting it.
4
Read in the new page: Load the requested page from disk into the chosen frame.
5
Pin and return: Increment the page's pin count (prevents it from being evicted while in use) and return the frame address to the requester.

Pin Count and Dirty Bit

  • Pin count: Counts how many threads/queries are currently using this page. A page can only be evicted when pin count = 0 (nobody is using it).
  • Dirty bit: Set to 1 when a page has been modified in memory but not yet written to disk. Ensures changes aren't lost.

Buffer Replacement Policies

When all frames are occupied (pinned or recently used), which page should be evicted to make room?

PolicyStrategyBest forWeakness
LRU (Least Recently Used)Evict the page that was accessed least recentlyMost general workloadsSequential flooding (see below)
MRU (Most Recently Used)Evict the most recently used pageRepeated sequential scansBad for general workloads
ClockApproximation of LRU with a reference bit and a "clock hand"General use, efficientStill vulnerable to sequential flooding
Sequential flooding: Suppose you have 10 buffer frames and scan a file with 100 pages, over and over. With LRU: each page request causes an I/O because the oldest page (which you'll need next) keeps getting evicted. You get 100 I/Os per scan. With MRU: after the first scan, later scans can reuse pages. MRU is much better here!

Why Not Just Use the OS File System?

The OS manages files and buffers too — so why does the DBMS need its own buffer manager?

  • OS can't pin a page (keep it guaranteed in RAM).
  • OS can't force a page to disk at a specific time (needed for crash recovery: Write-Ahead Logging).
  • OS doesn't support pre-fetching based on the access patterns the DBMS knows about.
  • Some OS filesystems can't span multiple physical disks.
  • OS file buffer replacement policy may not match the DBMS's needs.

2.6 — Record Formats

Records (rows) can be stored in two formats on a page:

Fixed-Length Records

All fields have the same size for every record (e.g., integers are always 4 bytes). Finding the i-th field requires a simple arithmetic calculation: Address = Base + L1 + L2 + ... + L(i-1). Simple and efficient.

Variable-Length Records

Fields can vary in length (e.g., VARCHAR). Two approaches:

  • Delimited fields: Use a special separator character between fields. Simple but finding the i-th field requires scanning from the start.
  • Field offset directory: Store an array of offsets at the start of each record pointing to where each field begins. Allows direct (O(1)) access to any field, and efficiently handles nulls (null fields can be stored compactly).

The field offset directory approach is preferred in modern systems because it's faster.

2.7 — Page Formats

Multiple records are stored together in a disk page. How are they organized within the page?

Fixed-Length Records on a Page

Two options:

  • Packed format: Records fill contiguous slots. Simple, but deleting a record leaves a gap — you must either compact or track gaps. Moving records changes their rid.
  • Unpacked format with bitmap: Keep a bitmap at the start of the page. Each bit indicates whether the corresponding slot is occupied. A deleted slot is just marked free in the bitmap. No compaction needed.

Variable-Length Records on a Page (Slot Directory)

This is the preferred format because it's flexible and allows records to move without changing their external rid.

The slot directory is stored at the end (or start) of each page. It contains:
• Number of slots
• A pointer to the start of free space
• For each slot: offset where the record starts within the page

Record ID = <page_id, slot_number>. If a record moves to a different position within the same page (for compaction), only the slot directory needs updating — the external rid (page, slot) remains unchanged.

2.8 — Heap File Implementations

The simplest file type is the heap file — records in no particular order. The DBMS needs to track which pages are in the file and which have free space.

Option 1: Doubly Linked List

Two linked lists: one for full pages, one for pages with free space. The header page holds pointers to the heads of both lists. Each page stores two pointers (prev/next) plus data.

Option 2: Page Directory (Better)

A collection of "directory" pages. Each directory entry records: a pointer to a data page + how many free bytes are on that page. The directory itself is a much smaller structure than the full linked list.

The Page Directory approach is far more efficient than the linked list for finding a page with enough free space for a new record. Instead of traversing a long list, you scan the compact directory.

2.9 — System Catalogs

The DBMS maintains catalog relations — metadata about all database objects. These are themselves stored as regular database relations!

  • For each relation: name, file name, file structure (heap/sorted), attribute names and types, index names, integrity constraints
  • For each index: structure (B+ tree, hash), search key fields
  • For each view: view name, view definition
  • Plus statistics (number of tuples, number of pages, etc.), authorization info, buffer pool size
The Attr_Cat relation stores attribute information:

Attr_Cat(attr_name, rel_name, type, position)

Example rows:
(sid, Students, string, 1)
(name, Students, string, 2)
(gpa, Students, real, 5)
(sal, Faculty, real, 3)

When you run SELECT name FROM Students WHERE gpa > 3.0, the query optimizer reads Attr_Cat to understand the Students schema before building an execution plan.
Chapter 10

Tree-Structured Indexes (B+ Trees)

The B+ tree is the most widely used index structure in database systems — almost every commercial DBMS uses it. It handles both equality and range searches efficiently, and adjusts gracefully when data is inserted or deleted.

3.1 — The Problem: Why Not Just Sort the File?

Suppose we want to find all students with GPA > 3.0. If the data file is sorted by GPA, we can do binary search — but this still requires log₂(N) page reads, which gets expensive when N is large.

Idea: Create a smaller "index file" that just contains key values and pointers to pages. Then do binary search on the smaller index file, and finally read just the data pages you need.

But the index file itself might be large. So we can apply the idea recursively — create an index of the index! This is the motivation for tree-structured indexes.

3.2 — ISAM: The Static Predecessor to B+ Trees

Before B+ trees, databases used ISAM (Indexed Sequential Access Method).

An ISAM tree is a static, multi-level index. Leaf pages contain the actual data entries. Non-leaf (index) pages contain <search key, pointer to child page> pairs that direct searches down to the correct leaf.

The structure is fixed at creation time. Inserts and deletes only affect leaf pages (via overflow pages). The non-leaf structure never changes.

ISAM Example

ISAM Tree — each node holds 2 entries
Root: 40
↙          ↘
20 | 33 51 | 63
↓ ↓ ↓ ↓             ↓ ↓ ↓ ↓
10*15* 20*27* 33*37* 40*46* 51*55* 63*97*
* = actual data entries (records)

ISAM Problem: Overflow Chains

After inserting 23*, 48*, 41*, 42*: the leaf pages fill up and overflow pages must be chained. If many inserts happen, chains become long and slow to search. Deletions can also leave empty overflow pages that waste space. ISAM degrades over time with updates.

ISAM's fatal flaw: it's static. Once built, the non-leaf structure never changes. Heavy insert activity creates long overflow chains that kill performance. This led to the invention of the dynamic B+ tree.

3.3 — B+ Tree: The Dynamic Solution

The B+ tree solves ISAM's problems by dynamically reorganizing itself when data is inserted or deleted.

A B+ tree of order d is a balanced tree where:

• Leaf pages contain the actual data entries, and are doubly linked (prev/next pointers) for sequential range scans.
• Non-leaf (index) pages contain key values and child pointers to guide searches.
• Every non-root node has between d and 2d entries (at least 50% full).
• The root can have as few as 1 entry.
• All leaf pages are at the same depth — the tree is always height-balanced.
• Cost to search: O(log_F N) where F = fanout (entries per page), N = number of leaf pages.

Typical order: 100. Typical fill factor: 67%. Average fanout = 133.

3.4 — Searching a B+ Tree

Search starts at the root and follows child pointers down to the leaf level:

1
At each non-leaf node, compare the search key with the entries in the node.
2
Follow the appropriate child pointer: the pointer between the two keys that bracket the search value.
3
Repeat until a leaf is reached. At the leaf, check if the entry exists.
Search for 15* in the example tree:
→ At root: 15 > 13, go right child (non-leaf node containing 17|24|30)
→ At that node: 15 < 17, go leftmost child (leaf with 14*,16*)
→ At leaf: 14* and 16* are there, but 15* is NOT. Answer: record not found.

Search for 28* in the tree from Ch8:
→ Root (17): 28 > 17, go right → node (5|13): 28 > both, go right → node (27): 28 > 27, right → leaf → 27*, 29* found. 28* not in tree.

Range query: all entries ≥ 24*:
→ Search for 24* → reach leaf with 24*. Then follow the "next" pointer to scan all subsequent leaves: 24*, 27*, 29*, 33*, 34*, 38*, 39*.

3.5 — Inserting into a B+ Tree

1
Find the correct leaf L where the entry belongs (same as search).
2
If L has space: Insert the entry. Done!
3
If L is full (overflow): Split L into L and a new leaf L2.
  • Redistribute entries evenly between L and L2.
  • Copy up the middle key to the parent (the middle key stays in L2's leaf AND a copy goes to the parent).
  • Insert a new index entry pointing to L2 into L's parent.
4
If parent is also full: Split the parent index node too.
  • Redistribute entries evenly.
  • Push up the middle key to the grandparent (unlike leaf split, the middle key is NOT kept in either child — it's pushed up and disappears from below).
5
If the root splits: Create a new root with one entry. Tree height increases by 1.
Copy-up vs Push-up — critical distinction!
• When a leaf node splits: the middle key is copied up — it stays in the leaf AND appears in the parent.
• When an index (non-leaf) node splits: the middle key is pushed up — it is removed from the child and only appears in the parent.

This difference exists because leaf entries are the actual data entries (or pointers to records). Index entries are just routing information.
Insert 8* into the example tree (root=13, left subtree: 5 → [2*,3*], [5*,7*]):

1. Search: 8 < 13, go left → non-leaf 5 → 8 > 5, go right → leaf [5*, 7*]
2. Leaf [5*,7*] has room. Wait — with order d=2, max is 2d=4 entries. [5*,7*,8*] = 3 entries. OK!

Actually in the textbook example the leaf is already full: [5*, 7*] and a split happens:
• Old leaf: [2*, 3*] — stays
• New leaf: [5*, 7*, 8*] must split → [5*, 7*] and [8*] wait... textbook shows:
• After split: left=[2*,3*], right=[5*,7*,8*] → this leaf splits → L=[5*] L2=[7*,8*], copy up 5
• Index entry 5 inserted into parent (was [5]), becomes [5,5] — too full → split, push up 5 to root
• Root had [13], now [5,13]... the tree grows wider then root itself splits creating a new root [17]

3.6 — Deleting from a B+ Tree

1
Find leaf L where entry belongs and remove the entry.
2
If L is still at least half-full (≥ d entries): Done!
3
If L is too empty (d-1 entries — underflow):
  • Try redistribution: borrow an entry from a sibling node (adjacent node with same parent). Update the parent key accordingly. Copy up the new separator.
  • If redistribution fails (sibling is also at minimum): Merge L with the sibling into one node.
4
If merge occurred: Delete the index entry pointing to the merged node from the parent. This can cascade upward, potentially reducing tree height.
Delete 19* from example tree (leaf contains 19*, 20*):
→ Remove 19*. Leaf now has [20*]. With d=2, minimum is d=2. Wait — if d=1 minimum is 1. [20*] is still valid. Done!

Delete 20* from same tree:
→ Leaf now has []. Underflow! Try redistribution: borrow from right sibling [22*, 24*]. Move 22* to left leaf, update parent key. Result: leaf=[20→22*], sibling=[24*], parent updated to 22.

Delete 24* (resulting in merge):
→ Remove 24* → leaf has []. Underflow. Sibling [27*, 29*] is at minimum, can't lend → MERGE.
→ Merge the two leaves. Parent loses the index entry separating them → "toss" that index entry.
→ Parent may also underflow → "pull down" the parent's separator from its parent to merge those index nodes.

3.7 — Prefix Key Compression

Index pages (non-leaf nodes) only need to direct searches to the right child — they don't need to store full key values. We can compress them.

Example: If consecutive index entries are "Dannon Yogurt", "David Smith", and "Devarakonda Murthy", we can abbreviate "David Smith" to "Davi" — the shortest string that is greater than "Dannon" and less than "Devarakonda".

Compression must maintain the rule: each index entry must be greater than every key value in any subtree to its left. "Dav" would be wrong if "Davey Jones" exists — we must use "Davi" at minimum.

Prefix compression allows more entries per page, increasing the fanout F, which reduces tree height and speeds up searches.

3.8 — Bulk Loading a B+ Tree

If you have a large dataset and need to build a B+ tree from scratch, inserting one record at a time is very slow. Bulk loading is far more efficient.

1
Sort all data entries by the search key.
2
Initialize: Create a root page and insert a pointer to the first sorted leaf page.
3
Process remaining sorted pages: Add index entries only along the rightmost path of the tree (one new entry per leaf page). When a rightmost index page fills, split it and push up.
Bulk loading advantages over repeated single inserts:
1. Fewer I/Os during build (writes are sequential, not random)
2. Leaf pages are stored sequentially on disk (better for future range scans)
3. Can control the fill factor (e.g., leave 33% free for future inserts)
4. Better for concurrency control (fewer lock conflicts during build)

Chapter 12

Overview of Query Evaluation

When you write a SQL query, the DBMS doesn't execute it naively. It generates multiple possible execution plans, estimates the cost of each, and picks the cheapest one. This chapter explains how that process works.

4.1 — What is a Query Plan?

A query plan (or query evaluation plan) is a tree of relational algebra operators, where each node specifies both the operation to perform (e.g., join, select, project) and the algorithm to use for that operation.

Operators are connected with a "pull" interface: when an operator needs its next output tuple, it "pulls" on its input operators, which in turn pull on their inputs, and so on recursively.
Think of a query plan like a factory assembly line. The final output is at the top. Each machine in the line "requests" parts from the machine below it. Data flows upward through the tree as each operator requests more input from its children.

4.2 — Key Algorithmic Techniques

Three core techniques are used repeatedly in query evaluation:

🗂 Indexing

Use WHERE condition predicates to retrieve only the tuples that match via an index, rather than scanning the whole table.

🔁 Iteration

Sometimes a full sequential scan is faster than using an index, especially when a large fraction of tuples qualify or when an index-only scan is possible.

🔀 Partitioning

Sort or hash the input to group related tuples together, replacing one expensive operation on large data with multiple cheaper operations on smaller pieces.

4.3 — Statistics and Catalogs

To estimate the cost of a plan, the query optimizer needs statistics about the data. These are stored in the system catalog:

  • NTuples(R): number of tuples in relation R
  • NPages(R): number of pages in R
  • NKeys(I): number of distinct key values for index I
  • Low(I), High(I): minimum and maximum key value in index I
  • Index height: levels in the B+ tree
  • Sometimes: histograms of value distributions for important attributes

Catalogs are updated periodically (not on every insert/delete — too expensive). The optimizer knows the statistics are approximate, but they're good enough for picking reasonable plans.

4.4 — Access Paths

An access path is a method of retrieving tuples. There are two types:

  • File scan: Read every page and check each tuple against the predicate. Always applicable.
  • Index scan: Use an index to find qualifying tuples quickly. Only applicable when the query predicate matches the index.

When Does an Index Match a Query?

Index TypeWhen does it match?Example
Tree index on <a, b, c> Query has terms on a prefix of <a, b, c> a=5 ✓ · a=5 AND b=3 ✓ · b=3 ✗ (not a prefix)
Hash index on <a, b, c> Query has equality terms on ALL attributes of the search key a=5 AND b=3 AND c=5 ✓ · a=5 AND b=3 ✗ · a>5 AND b=3 AND c=5 ✗

4.5 — Selections

Simple selections apply a predicate and return matching tuples.

Query: SELECT * FROM Reserves R WHERE R.rname < 'C%'

Assume 10% of names start with A or B, so 10% of tuples qualify = 100 pages worth, 10,000 tuples.

With clustered index on rname: ~100 I/Os (qualifying records are together)
With unclustered index on rname: up to 10,000 I/Os (one I/O per record — each on a different page!)

The difference is 100× — this illustrates why clustering matters so much for range queries.

The Most Selective Access Path Strategy

  1. Find the most selective access path — the index or scan that retrieves the fewest pages.
  2. Retrieve tuples using that access path.
  3. Apply any remaining predicates (those not matched by the index) as a filter on the retrieved tuples.
Query: WHERE day < '8/9/94' AND bid=5 AND sid=3

Option A: B+ tree index on day — matches the range condition day < '8/9/94'. Retrieve those tuples, then check bid=5 and sid=3 for each.

Option B: Hash index on <bid, sid> — matches the equality conditions bid=5 AND sid=3. Retrieve those tuples, then check day < '8/9/94' for each.

Which is better depends on selectivity. If bid=5 AND sid=3 matches very few records, Option B is better. If the date range matches very few records, Option A is better.

4.6 — Projection (Removing Duplicates)

The expensive part of SELECT DISTINCT is removing duplicates. Two approaches:

  • Sorting approach: Sort the result on all projected attributes, then scan linearly and remove consecutive duplicates. Can be optimized by dropping unwanted columns during the sort.
  • Hashing approach: Hash the result on projected attributes to create partitions. Load each partition, build an in-memory hash table, eliminate duplicates within partition.

If an index exists with all projected attributes in its search key, an index-only scan may avoid accessing the actual data at all.

4.7 — Joins

Joins are the most expensive and most important operation in query processing. Three main algorithms:

Algorithm 1: Index Nested Loops Join

If one relation (say S) has an index on the join attribute, use it as the "inner" relation.

foreach tuple r in R do foreach tuple s in S where r.join_col == s.join_col do add <r, s> to result

Cost: M + (M × pR) × (cost to probe S index)

  • Hash index probe: ~1.2 I/Os
  • B+ tree probe: ~2–4 I/Os
  • Finding matching S tuples: 1 I/O if clustered, up to 1 I/O per match if unclustered
Hash-index on sid of Sailors (as inner), joining with Reserves (as outer):
• Reserves: 1000 pages, 100 tuples/page → 100,000 tuples
• For each Reserves tuple: 1.2 I/Os for index + 1 I/O for the matching Sailors tuple
• Total: 1000 (scan Reserves) + 100,000 × (1.2 + 1) = 1000 + 220,000 = 221,000 I/Os

Algorithm 2: Sort-Merge Join

Sort both relations on the join attribute, then merge-scan them together.

1
Sort R on the join column.
2
Sort S on the join column.
3
Scan R and S together: advance R until current R-tuple ≥ current S-tuple, advance S until current S-tuple ≥ current R-tuple. When they match, output all combinations of matching R and S tuples (the "current group").

Cost: Sort cost for R + Sort cost for S + (M + N) for the final merge scan

Usually: M·log M + N·log N + (M + N). In extreme cases the final scan can be M×N if all tuples have the same join key.

Reserves (R=1000 pages) and Sailors (S=500 pages):
With 35 buffer pages: both can be sorted in 2 passes.
Sort Reserves: 2 × 2 × 1000 = 4000 I/Os
Sort Sailors: 2 × 2 × 500 = 2000 I/Os
Merge: 1000 + 500 = 1500 I/Os
Total: ~7500 I/Os

4.8 — Size Estimation and Reduction Factors

The optimizer must estimate how many tuples a query will produce to predict costs. For a query block:

Result cardinality = (max tuples) × (product of all reduction factors)

Maximum tuples = product of cardinalities of all relations in the FROM clause.

Reduction factors (RF) for common predicates:
• col = value: RF = 1/NKeys(I) (fraction of tuples with that specific value)
• col1 = col2: RF = 1/MAX(NKeys(I1), NKeys(I2))
• col > value: RF = (High(I) − value) / (High(I) − Low(I))

These assume independence between predicates — an approximation that works well enough in practice.

4.9 — The System R Optimizer

The most influential query optimizer design, still the basis for most modern optimizers.

  • Works best for up to 10 joins. Beyond that, the search space explodes.
  • Considers only left-deep plans — plans where every inner relation in a join is a base table (not the result of another join). Left-deep plans allow pipelining: the output of each join can flow directly into the next without being materialized to disk.
  • Avoids Cartesian products — only considers join orders where tables are connected by predicates.
  • Prunes the plan space using dynamic programming: keep the cheapest plan found so far for each subset of tables.
Motivating example — two bad plans vs good plan:
SELECT S.sname FROM Reserves R, Sailors S WHERE R.sid=S.sid AND R.bid=100 AND S.rating>5

Naive plan (nested loops, no pushdown): 500 + 500×1000 = 500,500 I/Os

Better plan (push selections down, sort-merge join):
• Apply bid=100 to Reserves → ~10 pages (T1), apply rating>5 to Sailors → ~250 pages (T2)
• Sort T1, sort T2, merge: ~3560 I/Os total

Best plan (with clustered index on bid):
• Use clustered index on bid to get 10 pages of matching Reserves tuples
• Use index nested loops with hash index on sid of Sailors
• Cost: 10 (fetch Reserves) + 1000 × 1.2 (probe Sailors index) = 1210 I/Os
Chapter 16

Transactions

A transaction is one of the most fundamental concepts in databases. It provides a way to group multiple operations into a single logical unit that either fully succeeds or fully fails — protecting data integrity even in the face of crashes and concurrent access.

5.1 — What is a Transaction?

A transaction is a unit of program execution that accesses and possibly updates various data items. A transaction represents a single logical work unit — for example, a bank transfer, a purchase, or an enrollment in a course.
Classic Example: Transfer $50 from Account A to Account B

1. read(A)
2. A := A - 50
3. write(A)
4. read(B)
5. B := B + 50
6. write(B)

Problem if step 3 succeeds but system crashes before step 6: $50 has been deducted from A but never added to B. The money is "lost"! The total (A+B) is no longer consistent.

Problem if another transaction reads A and B between steps 3 and 6: It sees A-50 and B (not yet incremented), so it thinks A+B is $50 less than it should be. This is an isolation violation.

5.2 — ACID Properties

Transactions must satisfy four properties, collectively called ACID:

A
Atomicity

Either ALL operations of the transaction are reflected in the database, or NONE are. No partial execution. If it crashes after step 3, we roll back to the original state.

C
Consistency

Execution of a transaction in isolation takes the database from one consistent state to another. The transaction must not violate integrity constraints. (A+B must remain unchanged after the transfer.)

I
Isolation

Concurrent transactions must behave as if each executed serially (one at a time). Intermediate results of a transaction must be hidden from other transactions.

D
Durability

Once a transaction commits, its changes are permanent — even if the system crashes immediately after. Changes are written to non-volatile storage.

5.3 — Transaction States

A transaction progresses through a well-defined lifecycle:

5.4 — Concurrent Execution: Why It's Needed

Running transactions one at a time (serially) is safe but wasteful. While one transaction waits for disk I/O, the CPU sits idle. Concurrent execution allows:

  • Better CPU/disk utilization: While T1 waits for a disk read, T2 can use the CPU.
  • Better response time: Short transactions don't have to wait behind long ones.
  • Higher throughput: More transactions per second.

But concurrency introduces the risk of transactions interfering with each other. The goal of concurrency control is to allow concurrent execution while ensuring correctness (serializability).

5.5 — Schedules

A schedule is a sequence of operations from multiple transactions, specifying the chronological order in which the operations execute. A schedule must include all operations of all transactions, and must preserve the relative order of operations within each individual transaction.

Serial vs Concurrent Schedules

In a serial schedule, one transaction completes entirely before the next begins. There is no interleaving.

Schedule 1 — Serial: T1 then T2 (A=1000, B=2000 initially) T1: read(A) A:=A-50 write(A) read(B) B:=B+50 write(B) T2: read(A) A:=A*0.9 write(A) read(B) B:=B*0.9 write(B) Result: A+B = (1000-50)*0.9 + (2000+50)*0.9 = 2700
Schedule 3 — Interleaved, but equivalent to Schedule 1 T1: read(A) T1: write(A) T2: read(A) T2: write(A) T2: read(B) T2: write(B) T1: read(B) T1: write(B) This interleaved schedule gives same result as Schedule 1 → it's serializable!
Schedule 4 — Interleaved, NOT serializable (INCORRECT) T1: read(A) A:=A-50 write(A) T2: read(A) read(B) print(A+B) ← sees inconsistent state! T1: read(B) B:=B+50 write(B) T2 reads A after deduction but before B is incremented → prints A+B = $1050 instead of $3000!

5.6 — Serializability

The key correctness criterion: a schedule is correct if it is equivalent to some serial schedule.

Conflicting Instructions

Two instructions conflict if they access the same data item AND at least one of them writes to it:

Instruction pairConflict?Why?
Ti: read(Q), Tj: read(Q)No conflictTwo reads never interfere
Ti: read(Q), Tj: write(Q)CONFLICTTj's write changes what Ti would read
Ti: write(Q), Tj: read(Q)CONFLICTTi's write changes what Tj reads
Ti: write(Q), Tj: write(Q)CONFLICTWhich write "wins"? Order matters.

Conflict Serializability

A schedule S is conflict serializable if it can be transformed into a serial schedule by repeatedly swapping adjacent non-conflicting operations.
Is this schedule conflict serializable?
T3: R(Q) → T4: W(Q) → T3: W(Q) → T4: R(Q)

Try to get to T3 then T4: Need to move T3's W(Q) before T4's W(Q). But T4's W(Q) conflicts with T3's W(Q). Can't swap!
Try to get to T4 then T3: Need to move T4's R(Q) before T3's R(Q). T4's R(Q) conflicts with T3's W(Q). Can't swap!
→ Not conflict serializable.

The Precedence Graph (Dependency Graph) Test

Test for Conflict Serializability:
1. Build a precedence graph: one node per transaction.
2. Draw an edge from Ti → Tj if Ti has an operation that conflicts with a later operation of Tj (i.e., Ti "goes before" Tj in the conflict).
3. The schedule is conflict serializable if and only if the precedence graph has no cycles.
Example schedule:
T1: R(A), W(A) | T2: R(A), W(A)
T1: R(B), W(B) | T2: R(B), W(B)

Conflict analysis:
• T1 R(A) before T2 W(A) → T1 → T2 (edge for A)
• T2 R(A) before T1 W(A) → T2 → T1 (edge for A)
• Same pattern for B...

Result: T1 → T2 AND T2 → T1 → cycle! NOT conflict serializable.

View Serializability (Broader)

Two schedules S and S' are view equivalent if for every data item Q:
1. The same transaction reads the initial value of Q in both schedules.
2. The same transaction performs the final write on Q in both schedules.
3. Every read of Q reads from the same writer in both schedules.

A schedule is view serializable if it is view equivalent to some serial schedule.
  • Every conflict serializable schedule is also view serializable (conflict ⊂ view).
  • Some schedules are view serializable but NOT conflict serializable — these involve "blind writes" (writes not preceded by reads of the same item).
  • Testing view serializability is NP-complete — no efficient algorithm is known.

5.7 — Recoverability

Even a serializable schedule can be problematic if transactions can abort after others have read their uncommitted writes.

Recoverable Schedules

A schedule is recoverable if: whenever Tj reads a value written by Ti, then Ti must commit before Tj commits. (No transaction commits based on data from an uncommitted transaction.)

Cascading Rollbacks Problem

Cascading rollback scenario T10: W(A) T11: R(A) W(A) T12: R(A) If T10 aborts → T11 must also roll back (read uncommitted data) → T12 must also roll back Three rollbacks from one failure!

Cascadeless Schedules

A cascadeless schedule ensures that Tj can only read a value written by Ti AFTER Ti has committed. This prevents cascading rollbacks entirely. Every cascadeless schedule is also recoverable.

5.8 — Isolation Levels in SQL

Full serializability can be expensive. SQL-92 defines four isolation levels that trade safety for performance:

Isolation LevelDirty ReadUnrepeatable ReadPhantom ProblemNotes
Read UncommittedPossiblePossiblePossibleMost permissive; no locking for reads
Read CommittedNoPossiblePossibleDefault in many systems (Oracle, PostgreSQL)
Repeatable ReadNoNoPossibleSame row always returns same value

  • Dirty read: Reading a value written by an uncommitted transaction.
  • Unrepeatable read: Reading the same row twice in one transaction and getting different values (another transaction committed an update in between).
  • Phantom problem: Re-running a range query in the same transaction returns different sets of rows (another transaction inserted/deleted rows that match the range).

5.9 — Transactions in SQL

  • A SQL transaction begins implicitly (no explicit BEGIN needed in standard SQL).
  • COMMIT WORK — makes all changes permanent and begins a new transaction.
  • ROLLBACK WORK — undoes all changes since the transaction started (aborts).
  • By default, most systems use auto-commit: each single SQL statement is its own transaction. This can be disabled: connection.setAutoCommit(false) in JDBC.
  • Isolation level: SET TRANSACTION ISOLATION LEVEL SERIALIZABLE
Chapter 17

Concurrency Control

Concurrency control is the mechanism that ensures multiple simultaneously executing transactions produce correct (serializable) results. This chapter covers locking protocols, deadlocks, multi-granularity locking, optimistic concurrency control, and timestamp-based methods.

6.1 — Conflict Serializable Schedules (Review)

Two schedules are conflict equivalent if they involve the same actions of the same transactions AND every pair of conflicting actions is ordered the same way in both schedules.

A schedule is conflict serializable if it is conflict equivalent to some serial schedule.

The dependency graph captures conflicts: there is an edge Ti → Tj if Tj reads/writes an object last written by Ti. Schedule is conflict serializable if and only if the dependency graph is acyclic.

6.2 — Two-Phase Locking (2PL)

The most widely used concurrency control mechanism. Every transaction must follow a strict locking discipline:

Lock Types

Lock ModeSymbolAllowsBlocks
Shared lockSMultiple readers simultaneouslyWriters (X)
Exclusive lockXOne writer exclusivelyAll other readers and writers
Two-Phase Locking Protocol:
1. A transaction must obtain an S lock before reading an object.
2. A transaction must obtain an X lock before writing an object.
3. A transaction cannot request new locks after it has released any lock.

This creates two phases: a growing phase (acquiring locks) and a shrinking phase (releasing locks). Once you release one lock, you can never acquire new ones.
Strict 2PL: A stronger version — all locks held by a transaction are released only when the transaction completes (commits or aborts). This ensures recoverability and cascadeless rollback.
Strict 2PL ensures only schedules with acyclic precedence graphs are allowed — i.e., only conflict serializable schedules. It's the most common protocol used in production systems.

6.3 — Lock Management

A dedicated lock manager component handles all lock requests. It maintains a lock table — a hash table indexed by object (data item). Each entry contains:

  • Number of transactions currently holding a lock on this object
  • Type of lock held (S or X)
  • A queue of pending lock requests

Lock and unlock operations must be atomic — no partial execution.

Lock upgrade: A transaction holding an S lock can upgrade to an X lock if no other transaction holds an S lock on the same object.

6.4 — Deadlocks

A deadlock is a situation where a cycle of transactions each waits for a lock held by the next transaction in the cycle. No transaction can proceed — they're all blocked waiting for each other.
Deadlock example:
T1: holds S(A), wants X(B)
T2: holds X(B), wants S(A)

T1 waits for T2 to release B. T2 waits for T1 to release A. → Deadlock!

Dealing with Deadlocks: Two Approaches

Approach 1: Deadlock Prevention

Assign priorities to transactions based on timestamps (older = higher priority). Two policies:

PolicyTi wants lock held by Tj. Ti is older (higher priority).Ti is younger (lower priority).
Wait-DieTi waits for TjTi aborts ("dies")
Wound-WaitTj aborts ("wounded" by Ti)Ti waits for Tj
Key rule: When a transaction restarts after being aborted, it keeps its original timestamp. This prevents starvation — an older transaction will eventually be old enough to proceed.
Approach 2: Deadlock Detection

Let deadlocks happen, then detect and resolve them:

1
Build a waits-for graph: one node per transaction, edge Ti → Tj if Ti is waiting for Tj to release a lock.
2
Periodically check for cycles in the waits-for graph.
3
If a cycle is found, choose a victim transaction to abort (typically the youngest, or the one with least work done), breaking the cycle.
Deadlock detection example:
T1: S(A) → wants S(B); T2: X(B) → wants X(C); T3: S(C) → wants X(A); T4: wants X(B)

Waits-for graph: T1→T2, T2→T3, T3→T1 → CYCLE! Deadlock among T1, T2, T3.
T4→T2 but T4 is not in a cycle.

Resolution: Abort one of T1/T2/T3 to break the cycle.

6.5 — Multiple Granularity Locking

Should we lock individual tuples, pages, or entire tables? Each has trade-offs:

  • Fine granularity (tuple-level): More concurrency, but high lock management overhead (thousands of lock requests per query).
  • Coarse granularity (table-level): Low overhead, but poor concurrency (one transaction blocks entire table).

Solution: Allow locking at multiple levels simultaneously, using special intention locks to signal intent at higher levels.

Intention Lock Modes

Lock ModeMeaningUse case
IS (Intention Shared)"I will place S locks on some descendant nodes"A transaction wants to read some tuples in this table
IX (Intention Exclusive)"I will place X locks on some descendant nodes"A transaction wants to write some tuples in this table
S (Shared)Read all tuples in this nodeFull table scan with no writes
SIX (Shared + Intention Exclusive)Read all tuples AND write some tuplesScan table and update some rows
X (Exclusive)Write all tuples in this nodeFull table update

Protocol Rules

  • To get S or IS on a node, must hold IS or IX on the parent.
  • To get X, IX, or SIX on a node, must hold IX or SIX on the parent.
  • When releasing, go bottom-up (most specific to most general).
  • When acquiring, start from root and go down.
T1 scans table R and updates a few tuples:
→ T1 gets SIX on R (will read all, write some), then S on each tuple it reads, then upgrades to X on tuples it updates.

T2 uses an index to read only part of R:
→ T2 gets IS on R, then S on each specific tuple it reads.

T3 reads all of R (full table scan):
→ T3 gets S on R. Much simpler than getting S on every individual tuple!

T1 and T2 are compatible (SIX vs IS = compatible — they can run concurrently!).
T1 and T3 are NOT compatible (SIX vs S = incompatible — T3 must wait for T1 or vice versa).

6.6 — The Phantom Problem

Even with Strict 2PL, there's a subtle problem with dynamic databases:

Phantom scenario:
T1 finds the oldest sailor with rating=1 (say age=71) and does more work.
T2 inserts a new sailor with rating=1 and age=96, then deletes the oldest sailor with rating=2.
T1 later finds the oldest sailor with rating=2 (say age=63).

Problem: There is no serial schedule T1→T2 or T2→T1 that gives this result! T1 has implicitly "locked the set of all sailors with rating=1" but a new one was inserted that T1 never saw.

This is the phantom problem: a transaction operates on a logical set of records, but Strict 2PL only locks the physical records that existed at the time.

Solutions to the Phantom Problem

  • Index locking: Lock the index page(s) that would contain the new record. T1 should lock the index page for rating=1 entries. T2's insert must also access (and lock) that page → conflict detected!
  • Predicate locking: Lock all records satisfying a predicate (e.g., rating=1). Index locking is a special case of this. Predicate locking is more general but has high overhead.

6.7 — Locking in B+ Trees

B+ trees present a special challenge: every search starts at the root, so the root would become a terrible bottleneck if we naively locked it for every operation.

Simple Algorithm (Inefficient)

Follow 2PL — lock each page as you traverse the tree, release when done. Problem: the root and upper levels must be locked for every search → terrible concurrency bottleneck.

Better Algorithm (Bayer-Schkolnick)

For Search: At each level, get S lock on child, then release S lock on parent.

For Insert/Delete (basic): Traverse with X locks. At each node, check if it's "safe" (won't need to split/merge):
• Safe for insert: node is not full
• Safe for delete: node is more than half-full
If child is safe, release all locks on ancestors (they won't be affected).

Even Better: Optimistic Tree Locking

Optimistic approach: First traverse the tree setting S locks (as if for search). Get to the leaf and set X. If the leaf is safe, proceed. If not safe (need to split), release everything and redo with X locks from the root.

Why better? In practice, splits are rare (67% fill factor means most insertions don't need a split). So most insert traversals only need S locks on the path — great concurrency!

Hybrid Algorithm

The likelihood that an X lock is actually needed decreases as we go higher in the tree. The hybrid approach uses different lock types at different levels:

  • Upper levels: S locks (likely not needed for modification)
  • Middle levels: SIX locks
  • Lower levels and leaf: X locks

6.8 — Optimistic Concurrency Control (Kung-Robinson)

Locking is a pessimistic approach — it prevents conflicts by blocking. If conflicts are rare (reads common, writes rare), locking overhead may not be worth it.

Optimistic CC: Instead of locking, let transactions run freely and check for conflicts only at the end.

Each transaction has three phases:
1. READ phase: Read from the database, but make all writes to private copies of objects.
2. VALIDATE phase: Check whether any conflicts occurred.
3. WRITE phase: If validation passes, make the private writes global (visible to others). If not, restart.

Validation: Three Tests

Transactions are assigned IDs at the end of their READ phase. Ti < Tj means Ti was validated before Tj.

TestConditionEnsures
Test 1 Ti completes entirely before Tj begins No overlap → trivially safe
Test 2 Ti completes before Tj starts its Write phase, AND WriteSet(Ti) ∩ ReadSet(Tj) = ∅ Tj doesn't read data written by Ti after Ti committed
Test 3 Ti completes READ phase before Tj, AND WriteSet(Ti) ∩ ReadSet(Tj) = ∅, AND WriteSet(Ti) ∩ WriteSet(Tj) = ∅ Neither dirty reads nor write-write conflicts

Serial Validation

To validate transaction T: check T against all transactions Ts that committed after T began:

valid = true -- S = set of Xacts that committed after Begin(T) < foreach Ts in S do if WriteSet(Ts) intersects ReadSet(T) valid = false if valid: install updates -- Write phase Commit T else: Restart T > -- critical section ends

Overheads of Optimistic CC

  • Must track ReadSet and WriteSet for every transaction.
  • Validation and write phase must be in a critical section (serialized).
  • Failed validations waste all the work done in the READ phase.
  • Work done on private copies may reduce clustering benefits.

6.9 — Timestamp-Based Concurrency Control

An alternative to locking: use timestamps to order transactions and detect out-of-order accesses.

Each transaction T is assigned a timestamp TS(T) when it begins.
Each data object O has two timestamps:
• RTS(O) — the timestamp of the most recent transaction that READ O
• WTS(O) — the timestamp of the most recent transaction that WROTE O

Rule: If action ai of Ti conflicts with action aj of Tj, and TS(Ti) < TS(Tj), then ai must occur before aj.

When T Wants to Read Object O

ConditionActionWhy
TS(T) < WTS(O)Abort and restart T with new (larger) TST is trying to read a value that a "newer" transaction has already overwritten — too late!
TS(T) >= WTS(O)Allow read; set RTS(O) = max(RTS(O), TS(T))T is reading a version that was written before T's timestamp — correct order.

When T Wants to Write Object O

ConditionActionWhy
TS(T) < RTS(O)Abort and restart TA newer transaction already read O — allowing T's write would violate timestamp order.
TS(T) < WTS(O)Thomas Write Rule: Safely IGNORE (skip the write!)O already has a newer version. T's write is obsolete — no one will ever read it. No restart needed.
TS(T) >= WTS(O) AND TS(T) >= RTS(O)Allow write; set WTS(O) = TS(T)No conflict — proceed normally.

Recoverability Issue with Timestamp CC

Timestamp CC can allow unrecoverable schedules — T2 reads a value written by T1, then T1 aborts. T2 has read garbage data. To fix this:

  • Buffer all writes until the writer commits.
  • Block readers until the writer of the version they want to read has committed.

6.10 — Multiversion Timestamp Concurrency Control

Multiversion CC: Instead of one version of each object, keep multiple versions. Writers create new copies; readers use an appropriate older version.

Key benefit: readers never block writers and writers never block readers.

For Readers (Reader Transactions)

Find the newest version of O with WTS ≤ TS(T) — the newest version that was written by a "past" transaction. Readers are never restarted (some version of every object always exists from "the beginning of time").

For Writers (Writer Transactions)

To write object O: find the newest version V with WTS(V) ≤ TS(T). If RTS(V) ≤ TS(T), create a new copy CV with WTS(CV) = TS(T). Otherwise (RTS(V) > TS(T)), reject the write — a newer reader has already read a version that this write would invalidate.

Old versions can be discarded when no active transaction could possibly need them (i.e., their timestamp is older than the oldest active transaction). Version maintenance has storage overhead but provides excellent read concurrency.
